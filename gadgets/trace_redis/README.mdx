# trace_redis

The `trace_redis` gadget traces [Redis](https://redis.io/) commands and replies
by parsing the [RESP](https://redis.io/docs/latest/develop/reference/protocol-spec/)
protocol on the TCP stream. For each request it shows the command, its key and
arguments; for each reply it shows a short summary, whether it is an error, and
the round-trip latency of the command that produced it.

This makes it useful for troubleshooting Redis clients: spotting slow commands,
failing commands (e.g. `WRONGTYPE`, `NOAUTH`, `OOM`), unexpected `(nil)`
responses (cache misses), and which container/pod is issuing them.

## Requirements

- Minimum Kernel Version : 5.7

  The gadget uses the `sock_ops` + `sk_skb` + `sk_msg` program types and a
  `BPF_MAP_TYPE_SOCKHASH` map (see [Parsing TCP-stream protocols](../gadget-devel/tcp-stream-gadgets.md)).
  Kernel BTF is required for the process/container enrichment.

## How it works

The gadget observes only the **client side** of a connection, i.e. sockets whose
port is the Redis port (`6379` by default, configurable with
`--operator-Sockhash-tcp-stream-ports`). On such a socket:

- commands the client **sends** are captured on the send path (`sk_msg`), and
- replies the client **receives** are captured on the receive path (`sk_skb`).

Only newly established connections are traced; connections that already existed
when the gadget started are not observed. Process/container enrichment covers the
active (client) side only.

Only the first 256 bytes of each RESP message are captured, which is enough for
the command verb, the key and short replies/errors — the value payload of a
large `SET` or the full body of a large reply is intentionally not captured.

## Flags

### `--operator-Sockhash-tcp-stream-ports`

Comma-separated TCP port(s) of the Redis server to trace. Connections whose local
or remote port matches are traced. Defaults to `6379`.

This flag is provided by the framework's `Sockhash` operator, which owns the
`sock_ops` program that selects sockets to track (see
[Parsing TCP-stream protocols](../gadget-devel/tcp-stream-gadgets.md)).

## Fields

The most relevant fields are:

- `type`: `command` (sent by the client) or `reply` (from the server).
- `command`: the Redis command verb (e.g. `GET`, `SET`, `HSET`).
- `key`: the first argument of the command (the key for most commands).
- `args`: the full argument list of the command (hidden by default; available in
  JSON output).
- `reply`: a short summary of the reply — a simple string like `OK`, an integer,
  `(nil)`, the error message, or the size of an aggregate (e.g.
  `(array: 6 elements)`, `(bulk: 5 bytes)`).
- `error`: `true` when the reply is a Redis error.
- `latency_ns`: time between the command being sent and its reply being received
  on the same connection (set on replies only).

## How replies are framed

Redis speaks RESP over a TCP **byte stream**: a single command or reply can be
any size and does not map to a single TCP segment. Unlike DNS-over-TCP, RESP has
no whole-message length prefix and no per-message framing — the first byte is
only a *type* byte (`+ - : $ * ...`), and those same bytes occur freely inside
payloads. There is therefore no reliable way to look at an arbitrary chunk of the
stream and tell whether it is the *start* of a reply or the *middle* of a large
one.

This gadget attaches to the reassembled TCP stream (via `sk_skb`/`sk_msg`), so
the bytes it sees are already in order and de-duplicated. However, it does **not**
install a `sk_skb/stream_parser`, so the receive-side verdict still runs once per
in-order segment. A large reply (for example the ~40&nbsp;KB `COMMAND DOCS`
response that `redis-cli` fetches at startup, an `array` of hundreds of elements)
spans many segments, and without framing each continuation segment would look
like a separate — and unparseable — reply.

To avoid emitting a burst of empty reply rows for one logical reply, the gadget
reports a reply **only when it matches an outstanding command** on the same
connection (recorded by the send path). The first segment of a reply consumes
that match and is emitted as a single event; later continuation segments of the
same reply find no match and are dropped. This keeps the output to one reply per
command and drives the `latency_ns` calculation, at the cost of the limitations
below.

## Limitations

- Only the client side of connections whose remote port is the Redis port is
  traced; server-to-server traffic and connections established before the gadget
  started are not observed.
- Only the first 256 bytes of each RESP message are parsed, so large keys,
  arguments and reply bodies are truncated (the `reply` field summarizes large
  replies as e.g. `(array: 872 elements)` rather than dumping the whole body).
- A reply is reported only if it can be matched to a preceding command on the
  connection (see [How replies are framed](#how-replies-are-framed)). As a
  consequence, **server-initiated data with no preceding command is not
  reported** — this includes RESP3 push messages, Pub/Sub deliveries
  (`SUBSCRIBE`/`PSUBSCRIBE`) and keyspace notifications.
- Latency and command↔reply pairing assume a **synchronous** request/response
  pattern (send a command, read its reply, repeat). With **pipelining** (several
  commands sent before their replies are read) only the most recent command's
  send time is retained, so latency is attributed approximately and some replies
  may be dropped. Proper pipelining support would require a `stream_parser` plus
  a per-connection FIFO of outstanding commands.
- TLS-encrypted Redis connections cannot be parsed, since the gadget observes the
  (encrypted) TCP stream.
